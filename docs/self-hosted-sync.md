# SQLite 自托管同步说明

## 存储与同步

浏览器通过同源 `/api/journal` 获取和保存记录，Node.js 事务性写入 `/data/journal.sqlite`。网页及 API 共用 8080 端口，无需独立数据库容器。豆卡、冲煮、设备和配方分别存为记录，照片随豆卡保存。语言和主题留在浏览器。

每 5 秒及页面重新获得焦点时检查服务器版本；无变化则不下载数据。打开编辑窗口时暂停刷新。保存先获取最新数据，合并不同记录的变化，再按版本号条件提交。同一记录已被另一设备修改时拒绝覆盖，保留表单，需重新打开最新记录后编辑。全量导入更新数据代次，拒绝旧页面覆盖新导入结果。

没有离线队列；保存失败不会退回浏览器私有存储冒充成功。

## 迁移和备份

先在旧地址导出备份，再在新实例导入。导入是替换全部记录，不合并多个设备。相同地址的浏览器旧记录在服务器为空时会提示确认迁移。旧浏览器数据不会自动删除；旧版后续产生的记录不会同步。

日常备份使用设置的 JSON 导出，包含照片。文件级备份应停止服务后复制整个数据目录，不直接复制运行中的单个 SQLite 文件。恢复时同样停止服务，并确保运行用户有目录写权限。保留旧备份便于回退；旧静态镜像不能直接读取 SQLite。

## 部署

命名卷挂载 `/data`，以非 root 身份运行。保持 Compose 项目名和卷名不变，重建容器不会删除记录。不要使用 `docker compose down -v`。单个应用实例管理一份数据库，不通过网络共享盘让多个容器共同写入 SQLite。

不加入登录，因此能够访问实例的人都可读写全部记录；项目公开不会让不同自托管实例共享数据。跨站写入检查不等同于身份认证。反向代理应保留 Host，必要时设置 `PUBLIC_ORIGIN` 为唯一公开来源地址。

## 当前限制

适用于单个共享咖啡空间。完整快照保存，单次请求最大 64 MiB，最多 10,000 条记录；大量照片会增加传输与内存占用。没有分页、独立照片存储、多账户、实时推送或离线队列。数据库使用 Node.js 内置 SQLite，无需 npm 运行依赖。

v1.3 发布镜像为 `tzbqweas/bean-journal:1.3`，`latest` 在本次发布时同步更新。服务每次启动生成实例标识，恢复数据库后页面会接受新实例的数据，旧表单需重新打开后保存。服务端模式配置缺失不会静默切换为浏览器私有存储。
